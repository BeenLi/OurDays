# Decision 0005 — 整个重复系列改时间，每一次沿用原来的记录

- **日期**：2026-11-24　**状态**：Accepted
- **范围**：`EventMirrorKeyPolicy.keptKeysForRescheduledEvents`；`SyncCoordinator.foregroundSync`；日历页的显示镜像

## 背景（原本的工作方式）
记录名是 `calendarIdentifier:eventIdentifier:occurrenceEpoch`，评论按记录名挂着（0004）。重复日程在系统日历里只有一条规则，每一次和它"原本的时间"都是按规则算出来的。规则从每周三 20:00 改成 21:00，每一次算出来的记录名全变：旧记录整批标成删除，新记录整批新建，评论留在旧记录上。

在日历里选"针对将来所有日程"时，系统还会把系列一分为二：前半段保留原来的事件 ID，后半段是一条新事件，事件 ID 也换了。0004 只处理了不重复的日程。

## 决策
记录名只在第一次上传时从系统日历算出来，之后本机的 `LocalEventShadow`（和自己的镜像）就是花名册：每条记着记录名，以及它现在对应哪个日历、哪个事件、哪一次。同步时，算出来的 key 本地没有的日程依次走三步：

1. **查花名册**：有一条活着的记录登记的正是这个日历、事件 ID 和发生时间，就用它的名字。系列搬过一次以后，每次同步都靠这一步。
2. **认搬家**：同一个事件 ID 下，新出现的几次和不见了的几条记录按时间最近互相配对，新的继承旧名字。相距必须小于这个系列自己的最小间隔（每周的系列是 7 天；只有一次时按一天），所以删掉一次、窗口里多出一次都不会被当成搬家。不重复的日程仍按 0004，只有一条候选就继承，不看距离。
3. **认分家**：一个花名册里从没见过的重复系列，和同一个日历里另一个系列不见了的记录按第 2 步的办法配对，条件是标题、地点、备注、链接完全相同（从 shadow 的 fingerprint 里取，没有 shadow 时从全部详情的镜像里取），而且这样的旧系列只有一个。

两条不变的规则保证记录名不会重复：一条日程自己算出来的 key 只要还活着就归它；继承来的名字不能是任何当前日程算出来的 key。旧系列又回到原来时间时，名字回到它那里。拿不准的都用自己的 key，结果和以前一样。

日历页只知道当前这一周，只做第 1 步（和 0004 的不重复日程），不做配对。系列刚搬完、还没同步时，那几次的评论暂时看不到，同步后回来。

## 备选与理由
- 按"整体平移了多少"来认：遇到夏令时、窗口边缘多一次少一次时不稳，按最近配对不需要先猜平移量。
- 分家时只看时间不看内容：同一个日历里删一个系列、建一个无关的系列会被接上，评论挂错地方比丢掉更糟。
- 在 shadow 上加"系列 ID"字段：本地表要迁移，而事件 ID、发生时间和 fingerprint 里已有的内容够用。
- 改记录名格式或迁移评论：同 0004，旧记录和旧版本都会断。

## 影响
- 云端记录名和字段都没变，旧版本照常读取，对方只看到同一批日程的时间变了。
- 和第二步的 `stableKey` 一致：记录名是身份，起了就不变；`stableKey`（外部 ID + 发生时间）和这里的事件 ID 一样只是找记录的线索，系列搬家时原地更新线索。别的设备按新的 `stableKey` 找到的还是这条记录。
- 改时间的同时改了标题、地点或备注的"将来所有日程"认不出来，后半段换新记录。
- 系列挪到相隔半个间隔以上的位置（每周三挪到下周一）时，按最近的一次配对，评论可能落在相邻的那一次上。
- 重装后的第一次同步用云端的自己镜像当花名册（0004）。镜像不记现在的事件 ID，分过家的系列要靠内容认回来，只有可见程度是"全部详情"的镜像带着完整内容，其他可见程度下后半段会换新记录。
- 2026-11-25 在模拟器上实测：对每日系列的第 3 次选"将来所有日程"挪后一小时，第 3 次起换了新的事件 ID，前两次保留旧 ID；再把后半段从它的第一次起整体挪动，事件 ID 不变，只有发生时间变。两种情况下两边的评论和记录名都保留（冒烟脚本 9d）。
