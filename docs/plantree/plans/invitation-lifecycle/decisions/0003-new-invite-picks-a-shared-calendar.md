# Decision 0003 — 「+」新建日程：可邀请也可只建自己的，日历自己选，发送不等 iCloud

- **日期**：2026-11-26　**状态**：Accepted
- **范围**：`CreateInviteView`、`InviteCalendarChoicePolicy`、`CalendarAccessService.createEvent(from:inCalendarWithID:)`

## 背景（原本的工作方式）
日历页右上角的「+」打开「新建邀请」：填标题和时间，App 在系统日历里建一条日程，同时发出邀请。日程固定建在 App 自己创建的粉色日历「ShareCal」里，没有就新建一个。发送要等日程和邀请都上传到 iCloud 才关闭，失败就停在表单上。表单里看不出邀请发给谁，未配对时也能点发送，邀请发给一个不存在的对方。

## 决策
1. 表单多一行「日历」，列出**已经打开共享、并且可写**的日历。默认值依次是：上次选的、系统默认日历、App 自己的日历、第一个。选择记在本机（`SettingsStore.lastInviteCalendarID`）。
2. 没有任何可写的共享日历时，不显示这一行，照旧建在 App 自己的日历里并把它打开共享。
3. 多一行「邀请 TA」开关，显示对方头像和昵称，配对后默认打开。关掉就只在自己的日历里建一条日程，不发邀请，标题变成「新建日程」，按钮变成「添加到日历」，也不再限制日程必须尚未结束。未配对时开关关着且不可点，提示「配对后才能发出邀请」，仍然可以建自己的日程。
4. 发送改成和日程详情里一样的乐观发送（calendar-ux-fixes 0002）：日程写进日历、邀请存进本地就关闭，上传在后台做；失败时 `needsCloudKitUpload` 留着，下次同步重传。
5. 发送按钮从导航栏的纸飞机图标改成底部的文字按钮。

## 备选与理由
- 列出所有可写日历：选了没共享的日历，对方看不到这条日程，除非顺手把整个日历打开共享，这会把里面别的日程也一起给对方。所以只列已共享的。
- 「+」做成菜单，分「新建日程」和「邀请 TA」两项：两张表单除了发不发邀请完全一样，多点一次不值得，用户（2026-11-26）也确认一个入口两种用法。
- 继续只用「ShareCal」日历：日历是数据的来源，用户自己的日历才是他平时看的地方，多出一个陌生的日历反而要解释。

## 影响
- 老用户第一次打开表单，默认日历可能从「ShareCal」变成系统默认日历（前提是它已共享）。
- 断网时也能发邀请，联网后的下一次同步补传。
