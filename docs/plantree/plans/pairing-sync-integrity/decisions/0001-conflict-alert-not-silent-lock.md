# Decision 0001 — 配对更换：多出的参与者进冲突弹窗，不再静默移除

- **日期**：2026-10-21　**状态**：Accepted，#4 已落地
- **范围**：同步管线里的配对裁决、我方分享的参与者处理

## 背景（原本的工作方式）
A 与 B 已配对，A 把邀请链接发给 C，C 加入了 A 的分享。A 下一次同步会先拉取我方分享的参与者，并带着已存的伴侣 id 做"两人锁"：伴侣之外的人一律静默移除，于是 C 被踢掉。随后 A 打开 C 的分享确认「更换配对」，流程又把 B 移除，A 的分享里一个人都不剩，C 必须重新点一次链接。C 加入 A 的分享与 A 打开 C 的链接没有固定先后，自动踢人总是先于 A 的决定执行，所以只保护"待确认的那个人"不够。

## 决策
1. 删除静默移除；拉取我方参与者变成只读。
2. 只要我方分享里出现伴侣之外的人，就报配对冲突（已配对时是"外出/进入不一致"，还没互相分享时是"多个参与者"）。冲突期间上传/导入都暂停，用户在已有的「配对冲突」弹窗里选择保留谁。
3. 保留的人不是原伴侣时，清掉原伴侣的备注名、头像、配对日期等本地状态，与「更换配对」确认路径共用同一段清理。

## 备选与理由
- (否决) 只保护待确认的替换对象：顺序不定，仍会踢错人。
- (否决) 自动保留最新加入者：这是用户的决定，不该由同步代劳。

## 影响
- `CLAUDE.md` 的配对铁律同步更新："多余的参与者永远不自动移除"。
- 端到端复现需要第三个 iCloud 账号，冒烟脚本不覆盖。
