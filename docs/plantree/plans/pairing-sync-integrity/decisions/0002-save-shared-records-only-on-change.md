# Decision 0002 — 共享 zone 里的记录只在真正变化时保存

- **日期**：2026-10-23　**状态**：Accepted，#20 已落地
- **范围**：根记录（CoupleSpace root）、MemberProfile 的保存路径；对以后所有共享记录写入的规则

## 背景（原本的工作方式）
1.5 上线后用户发现对方的头像要很久才同步过来（最终能到，昵称正常）。排查排除了 schema、本地覆盖、1.5 与 main 的头像逻辑差异。真正的原因：每次已配对的同步都会无条件重写两条共享记录——根记录每次重新赋 ownerMemberID 再保存，MemberProfile 每次把 `updatedAt` 设成现在再保存。两条记录都在被共享的 zone 里，每次保存都会触发对方 shared-database 订阅的静默推送；对方的推送处理跑一次完整同步，又重写自己的两条记录，再推回我这边。这个 sync → push → sync 的乒乓一直进行，烧光 iOS 的静默推送预算，真正的改动（新头像）被排在后面，前台打开又常落在 60 s 节流窗口里。

## 决策
1. 根记录只在 ownerMemberID 与现有值不同时写入，并返回是否改动；没变就跳过保存。
2. MemberProfile 只写有变化的 key；只有别的 key 变了（或记录是新的）才更新 `updatedAt`；`changedKeys()` 为空的已有记录跳过保存。
3. 把记录挂到父记录的操作幂等（同一个 parent 不重复设置）。
4. **规则**：以后往同步管线里加任何共享记录写入，都要先和取回的记录比对，没变化就不保存。

## 影响
- 创建根记录、第一次写 profile、昵称或头像真的变了，这些路径行为不变。
- README 曾有一节「为什么要只写变化」，后在 #26 精简掉；规则保留在 `CLAUDE.md` 与本决策。
