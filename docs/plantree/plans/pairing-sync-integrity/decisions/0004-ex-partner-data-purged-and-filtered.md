# Decision 0004 — 解除配对：删掉前任的记录，导入时再过滤一层

- **日期**：2026-10-23　**状态**：Accepted，#23 已落地
- **范围**：解除配对、配对冲突里"保留新人"、三类记录的导入

## 背景（原本的工作方式）
我 private zone 里的每条记录都挂在唯一的共享根记录下，所以给新伴侣创建的 CKShare 会暴露前任留下的一切：他对我事件的评论、我们互发的邀请和历史访问申请。解除配对只删我的 CKShare 和对方的缓存镜像。UI 把"不是我"的 member id 一律当作"对方"渲染，于是：在新伴侣的设备上，前任的评论读起来像**我**说的，我给前任的待处理邀请新伴侣可以回答；在我的设备上，前任的评论从 private zone 反复导入、显示成新伴侣的名字和头像，前任的邀请缓存也活过了解除配对。

## 决策
1. **离开时删**：解除配对和冲突里保留新人时，删掉我 zone 里非我写的评论、全部邀请与历史申请的传输记录（两人制里它们都只和那个人有关；我对自己事件的评论保留），并清同样的本地缓存。清理失败也先清本地状态，失败留日志。
2. **导入时过滤**：另一方是真实 `_` 前缀 userRecordID、却既不是我也不是现任的评论/邀请/申请，一律丢弃（占位 id 放行）；导入后再对缓存做一次同样的清理，即使云端清理失败也不会显示出来。

## 影响
- 需要第三个 iCloud 账号才能端到端验证"解除 → 换人 → 重配"，单元测试覆盖两层规则。
- README「数据安全」一节回答了"解除配对后数据有什么变化"（#26）。
