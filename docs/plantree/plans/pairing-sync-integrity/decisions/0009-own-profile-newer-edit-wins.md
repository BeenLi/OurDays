# Decision 0009 — 同一 Apple ID 的两台设备：自己的昵称和头像按修改时间合并

- **日期**：2026-11-23　**状态**：Accepted　**PR**：#56
- **范围**：`MemberProfile` 中自己的那条记录，`SettingsStore.currentDisplayName` / `currentAvatar`

## 背景（原本的工作方式）
自己的昵称和头像只存在本机的 UserDefaults 里。每次配对同步都把它们写进自己 zone 的 `MemberProfile`（#20 之后只在值不同时才写）。平时的同步只导入对方的 zone，从来不读回自己的这条记录。

只有一台设备时这样没问题。但同一个 Apple ID 可能同时装在两台设备上（今天已经可以是 iPhone 加兼容模式的 iPad，以后还可能有 Mac）：在 A 上换了头像，B 本机还是旧的，B 一同步就判断「和云端不一样」，把旧头像写回去。A 的写入还会通过私有库订阅推送给 B，B 的写回又推送给 A 和对方，形成 #20 那种来回同步。

## 决策
1. 本机记下自己最后一次改昵称或头像的时间（`currentProfileUpdatedAt`）。
2. 同步写 `MemberProfile` 之前先读云端这条记录（`OwnMemberProfileMergePolicy`）：
   - 和本机相同：不写。
   - 云端的 `updatedAt` 更新：不写，改为采用云端的值，同时记下云端的时间。
   - 本机更新：照常写入，`updatedAt` 用本机的修改时间。
3. 升级前装的 App 没有修改时间。如果它和云端不一样，就采用云端，因为对方看到的就是云端这份。
4. 重装恢复（#22）恢复资料时，同样记下云端的时间。

## 备选与理由
- 把昵称和头像改存到 `NSUbiquitousKeyValueStore`：要多一套同步，可靠性也不受我们控制，而 `MemberProfile` 本来就是这份数据的权威来源。所以不采用。
- 每次同步都无条件拉回自己的资料：本机刚改完、还没上传时会被云端旧值覆盖。按时间比较可以同时处理两个方向。

## 影响
- 只有一台设备的用户看不出任何变化。每次配对同步多读一条很小的记录。
- 两台设备时，后改的一方生效，另一台在下一次同步（或收到推送）时跟上，不会再来回覆盖。
- 两台设备的时钟如果差很多，可能是时钟慢的那台输掉。资料编辑很少同时发生，可以接受。
