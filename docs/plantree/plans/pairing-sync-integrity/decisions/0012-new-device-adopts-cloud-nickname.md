# Decision 0012 — 新设备先用云端已有的昵称，不再先让用户起名

- **日期**：2026-11-24　**状态**：Accepted　**PR**：#59
- **范围**：首次启动时的「设置我的昵称」弹窗（`RootView.reevaluateRootSheetFlow`），自己的 `MemberProfile`

## 背景（原本的工作方式）
首次启动时，本机没有昵称就立刻弹「设置我的昵称」，这一步排在查云端数据之前。0003 的设计是：先起名，再弹「发现旧的 iCloud 数据 → 继续使用」，把云端的昵称恢复回来。

0009 之后，自己的资料按修改时间合并，后改的赢。于是同一个 Apple ID 的第二台设备（Mac、iPad）或重装后的 iPhone 上，刚填的昵称（点「跳过」则是随机昵称）成了最新的一份，同步时把伴侣认识的那个昵称覆盖掉。在 Mac 上实测时就出现了：Mac 写入随机昵称，iPhone 随后判定「云端更新」而采用了它。

## 决策
1. 首次启动、本机没有昵称、CloudKit 可用时，在决定是否弹「设置我的昵称」之前，先读一次自己 zone 里的 `MemberProfile`（`InitialProfileCloudLookupPolicy` + `ExistingICloudDataIdentityRecovery.restoreOwnProfile`）。每次启动只读一次。
2. 读到了就直接采用这个昵称和头像，并记下云端的 `updatedAt`（和 0003 的恢复一样），不弹起名。0003 的「发现旧的 iCloud 数据」提示照常出现。
3. 没读到（全新用户）或读取失败（离线）时，照旧弹出让用户起名。
4. 查询期间用户若已经自己填了名字，以用户填的为准。查询进行中，其他触发的流程不弹起名。

## 备选与理由
- 只改 0009，让「首次起名」不算一次编辑：首次起名和以后改名在本机无法可靠区分（重装、清数据都会回到首次），而且新设备上仍然会白白问一次名字。所以不采用。
- 把 0003 的「发现旧的 iCloud 数据」提示挪到起名之前：那个提示要先完成成员 ID 和多次查询，等待更久；而且用户选「删除」时还需要起名。只提前读昵称更简单。所以不采用。

## 影响
- 全新用户：首次启动多一次很小的查询（通常一两秒），之后照旧起名。
- 第二台设备和重装：不再问名字，直接沿用伴侣认识的昵称。
- 已经被覆盖的昵称不会自动改回，需要用户在任一设备上重新改一次。
