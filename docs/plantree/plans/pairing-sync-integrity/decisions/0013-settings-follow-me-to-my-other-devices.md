# Decision 0013 — 同一 Apple ID 的另一台设备直接接着用：设置跟着人走

- **日期**：2026-11-24　**状态**：Accepted　**PR**：#61

## 背景（原本的工作方式）
配对、双方日程、评论、邀请和自己的昵称头像都在 CloudKit 里，跟着 Apple ID 走。但还有几样只存在本机的 UserDefaults 里：给对方的备注名、给对方设的头像、选了哪些日历、新日程对对方的默认可见程度、手动选的语言、动态已读位置。

Mac 版（0010、0011）让同一 Apple ID 有了第二台常用设备。Mac 首次打开时这些都回到默认值，还会再弹一次「设置备注」「配对安全提示」，以及「发现旧的 iCloud 数据：继续使用 / 删除」。在 Mac 上点「删除」会删掉 iPhone 正在用的数据区。

选中的日历存的是本机的 `calendarIdentifier`，每台设备不同，不能直接搬。

## 决策
1. **私有设置记录。** 在私有库新建一个不共享的 zone `OwnDevices`，里面一条 `OwnSettings` 记录，`payload` 是 JSON。`CoupleSpace` 里的记录都挂在共享根记录下，对方能读，所以不能放在那里。
2. **按部分合并，后改的赢**（同 0009）。备注名和对方头像、日历选择、默认可见程度、语言各带一个编辑时间；时间相同保留云端，避免两台设备互相写回。已读位置取较晚的。编辑时间取整到秒，保证往返后相等，不变就不写。
3. **只有人的操作才算编辑。** 自动选中 ShareCal 日历、从另一台设备采用设置都不更新编辑时间。升级前设置过的项按「最早的编辑」参与合并：能传给新设备，但输给任何一次真实编辑。
4. **备注名按伴侣记。** 记录里带伴侣的成员 ID，只在同一位伴侣时采用；采用时把「设置备注」「配对安全提示」视为已看过。新设备在同步中途才知道伴侣是谁，所以在确定伴侣的同一时刻再采用一次，提示不会先弹出来。
5. **日历按「账户 + 日历名」对应**（`EKSource.title` + 日历标题）。同一账户下有两个同名日历时跳过，不猜。记录保留这台设备没有的日历，这台设备只改自己看得到的那部分。一个都对不上时，保留本机原来的选择。设置页列出另一台设备上打开、本机没有的日历。
6. **第二台设备不再问「继续使用 / 删除」。** 云端已有这条设置记录，说明另一台设备正在用这些数据，直接继续使用。删除入口仍在设置的「数据与恢复」里。
7. **Mac 显示 iPhone 分享的全部日程。** Mac 本地没有的日历（「我的 iPhone」、只在 iPhone 登录的账户）里的日程，从云端副本显示，可评论。Mac 本地已显示的同名日历里对不上的云端副本不显示，那是 Mac 上改过、iPhone 还没重新上传的。
8. 设置同步失败（离线、Production 还没部署这个记录类型）只记日志，不让同步失败。

## 备选与理由
- `NSUbiquitousKeyValueStore`：新设备上什么时候到达不可控，首次启动没法等它；以后要放「补完别名」标记和设备活跃时间（见方案第二步）需要可靠读取；照片头像受 1 MB 总量限制。0009 也因为可靠性没用它。
- 设置放进 `MemberProfile`：那条记录对方能读，备注名是写给自己看的。
- 日历只按标题对应：iCloud 和 Google 里常有同名日历（「家庭」「工作」）。

## 影响
- 需要把 `OwnSettings` 记录类型部署到 Production。没部署时设置不接力，其他同步不受影响。
- 升级后的 iPhone 第一次同步会写入这条记录；Mac 在那之后首次打开才能直接接着用。
- 「我的 iPhone」「我的 Mac」本地日历两边名字不同，不会对应；只在 Mac 上的日历仍然不能分享，等第二步（全局编号）。
- Mac 上两条标题和时间完全相同、又对不上 key 的日程，可能显示两次。
