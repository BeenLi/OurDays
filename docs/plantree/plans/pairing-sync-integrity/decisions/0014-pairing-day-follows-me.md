# Decision 0014 — 配对天数跟着人走

- **日期**：2026-11-24　**状态**：Accepted

## 背景（原本的工作方式）
配对日期（「配对第 N 天」和「自 … 起」，也决定从哪天开始分享日程）只存在本机。
- 看着配对完成的设备：在第一次同步到伴侣时记下当天。
- 新设备（同一 Apple ID 的 Mac）：在自己第一次同步时记下当天，所以从第 1 天算起。
- 重装或走「继续使用旧数据」的设备：用共享根记录的创建日期反推。那是发出邀请的日子，对方晚几天接受，就会多算几天。

0013 让设置在自己的设备之间接力，但没有包括配对日期。

## 决策
1. 配对日期放进 `OwnSettings` 的 JSON，带伴侣的成员 ID。只有同一位伴侣才采用。不新增 CloudKit 字段，不用部署 Schema。
2. **同一位伴侣，取最早的那天**：后加入的设备只能记下自己第一次同步的日子，总是偏晚。伴侣不同时取较新的配对。
3. **反推的日期不上传**：本机记一个「这是反推的」标记。收到接力的日期时，无条件替换反推的日期。
4. **解除配对或换伴侣时记下时间**（较晚的赢）。在那一天之前开始的配对不再接力，也不会被采用。这样和同一个人重新配对时，会从新的一天算起，而不是被旧日期拉回去。

## 备选与理由
- 后改的赢（同 0009、0013）：新设备第一次同步记下的日期是「后改」，会盖掉 iPhone 的正确日期。
- 两边都取最早，包括反推的日期：反推的日期本来就偏早，会把错误传给所有设备。
- 只用共享根的创建日期：就是现在偏早的那个。

## 影响
- 1.9 的设备读到新字段会忽略。它真正改了设置要回写时会丢掉配对日期，下一次新版本同步会补回来，只多写一次，不会来回覆盖。
- 在这之前重装过的设备，日期本来就是反推的，但没有标记，所以按「看到的」参与合并（取最早）。
