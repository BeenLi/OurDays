# Decision 0015 — 发起配对撞上别处刚建好的分享时，直接用那个分享

- **日期**：2026-11-25　**状态**：Accepted

## 背景（原本的工作方式）
「发起配对」先读根记录：有分享就复用；没有就把根记录和新分享放在一个原子批次里保存（`saveNewShare`）。读和存之间隔着几秒网络往返。同一个 Apple ID 的两台设备（iPhone + Duo/Mac）同时点，或者同一台设备在界面 30 秒超时后又点一次而第一次还在跑，后到的那次会被服务器拒绝，用户看到报错。原子批次里根记录只显示被连带的 "Atomic failure"，真正的原因在分享记录上（1.9 一位 iPhone Duo 用户看到的就是这条）。

## 决策
1. 横幅显示批次里真正失败的那条记录的错误，不再显示 "Atomic failure"；CloudKit 错误都附上错误码和 request id。
2. `saveNewShare` 失败且错误可能是撞车（alreadyShared、serverRecordChanged、serverRejectedRequest）时，重新读一次根记录：已经有分享就复用它，不报错；仍然没有就照常报错。

## 备选与理由
- 加锁或排队：跨设备无法加锁；本机排队解决不了两台设备。
- 失败后自动重试保存新分享：根已经有分享时会一直失败。

## 影响
- 两台设备最终用同一个分享链接，配对不受影响。
- 还没证实那位 Duo 用户就是撞车；如果不是，新横幅会给出真正的错误码。

## 补充（同日）
3. **读根记录被拒不再当作「没有根记录」**：以前 `serverRejectedRequest` 和 `unknownItem` 一样，会新建一个根记录覆盖云端那个（它可能已经挂着分享），接着再建分享就被拒。中国区与美区之间的请求偶尔会瞬时返回 15（见 notifications/0003）。现在只有 `unknownItem` 算没有；被拒、限流、网络错误最多重试 3 次（间隔 2 秒），仍失败就报错。
4. 日程镜像的保存、删除和批量读取都按每批 200 条拆开发（CloudKit 单次请求上限 400 条），第一次同步记录很多时不再整批失败。
