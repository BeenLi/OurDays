# Decision 0017 — 每台设备都上传自己的日程，Mac 先认领 iPhone 已有的记录

- **日期**：2026-11-25　**状态**：Accepted
- **范围**：`OwnEventUploadPolicy`、`OwnRecordAdoptionPolicy`、`OwnRecordUploadFilterPolicy`；`SyncCoordinator.foregroundSync` 中自己日程的生成、上传、对账删除和硬删除；`OwnRelayedSettings.macUploadsOwnEventsAt`

## 背景（原本的工作方式）
记录名起了就不变，评论挂在上面（comment-visibility 0004、0005）。它来自设备本地的日历 ID 和事件 ID，所以 Mac 不上传（0010），只显示 iPhone 上传的那份（0011）。只在 Mac 上的日历（「我的 Mac」、只在 Mac 登录的账户）不能分享；Mac 上新建的日程要等 iPhone 下次同步，对方才看得到。0016 给每条记录加了跨设备一致的 `stableKey`。

## 决策
1. **都上传，先认领。** 同步时，这台设备还没在云端确认过的日程（没有已上传的 shadow），先按 `stableKey` 找我的 zone 里已有的记录：有活着的就用它的记录名，不另起一条。云端只有已删除的那条（另一台设备删了，这台的日历还没跟上），这次既不上传也不算删除（"按住"），删除不会被撤回。都没有才起新记录。读了整个 zone 的设备，只有云端真有这条记录才算确认过（一次没看到任何日程的同步可能把 shadow 记成已上传，单凭这个不算）；这台设备自己删掉的记录，日程又出现时直接复用。
2. **Mac 起的新记录名以 `mac:` 开头。** 两台设备同时给同一条日程起了记录（都还没看到对方的），能看到整个 zone 的 Mac 会挪到胜出的那条：先 iPhone 的（`mac:` 开头或从 Mac 本机日历写的都算 Mac 的），再比名字小的；自己那条按正常的删除流程打上墓碑。iPhone 的记录总是胜出，所以 iPhone 不用看整个 zone。
3. **Mac 什么时候能起新记录。** 只有当我 zone 里每条活着的记录都带 `stableKey` 时（iPhone 已升级并补完，0016）。否则 Mac 只更新能认领到的记录，其他日程按住，效果和 0010 一样。旧版本的设备一旦又写了不带编号的记录，Mac 自动退回。
4. **iPhone 什么时候去查。** Mac 上传时在私有设置里记一个时间（`macUploadsOwnEventsAt`，后的赢，一天最多改一次）。45 天内有这个时间，iPhone 遇到还没确认过的日程时，按它们的 `stableKey` 查一次（只查这些，不读整个 zone）。上传确认过的日程一下子都不在了（比如重新登录 iCloud 后日历 ID 变了），iPhone 也查一次，好接回原来的记录和评论。没有 Mac 的用户平时不多花这一次查询。查询失败就照旧起新记录，由 Mac 按第 2 条让开。
5. **云端已经是这样就不写。** 有云端副本可比的时候，内容相同（日历 ID 是本机的，不算）就不再写；刚认领来的记录，这台设备上的内容即使不同也先不写，以云端为准，等这台设备上真的改了再上传（这台的日历可能只是还没同步到最新）。比对过、没有要写的，只有云端确实有的那些 shadow 记为已上传。
6. **只删自己管的。** 硬删除（超出分享范围）只删这台设备上传确认过的记录。对账删除仍按本机日历 ID 过滤，别的设备写的记录不会被这台删掉。过期墓碑的清理（0019）也一样：只清这台设备确认过的，或最后从本机日历写入的，Mac 不清 iPhone 的，反过来也一样。30 天的保留期让第 1 条的「按住」照常起作用。
7. **Mac 存的自己镜像** = 这次自己生成的 + 云端其余的记录（只在 iPhone 上的日历、被按住的）。Mac 每次同步都读整个 zone（以前也是），现在在生成 key 之前读，同步后不再读第二次。

## 备选与理由
- 只让一台设备上传（0010）：Mac 独有的日历永远分享不出去，Mac 上新建的日程要等 iPhone。
- 每次同步所有设备都读整个 zone 来认领和去重：最稳，但 iPhone 的同步本来就慢，没有 Mac 的用户白白多一次全量读取。等增量同步（change token）做好后，读 zone 的代价变小，可以再放宽。
- 起记录前统一问 `OwnSettings` 里的对照表：要两台设备一起改一条记录，冲突多（见 0016）。
- 冲突时按记录创建时间定胜负：同时起的两条谁先谁后不确定，iPhone 不看整个 zone，碰到自己输的情况没人纠正。用 `mac:` 前缀定胜负，看得到全局的 Mac 永远是让开的一方。

## 影响
- 对方看到的每条日程仍只有一份。Mac 上新建的日程、只在 Mac 上的日历，Mac 同步后对方就能看到。
- iPhone 不显示只在 Mac 上的日历里的日程（它们不在 iPhone 的系统日历里，iPhone 也不读整个 zone）；对方能看到。增量同步之后再补。
- 两台设备几乎同时第一次上传同一条日程时，Mac 那条会被删掉，那几秒里对方在上面的评论会丢；之前 iPhone + iPad 两边都上传留下的重复记录，Mac 看到时会合成一条，输掉那条上的评论也会丢。
- 外部 ID 两边对不上（0016 的 Exchange 风险）时，Mac 会多起一条记录，对方看到两次。
- 旧版本（1.9）的 iPhone：Mac 不起新记录（第 3 条），退回 0010 的效果。旧版本的 Mac：不上传，和以前一样。
- 不需要新的 CloudKit 字段：`macUploadsOwnEventsAt` 在 `OwnSettings` 的 JSON 里；按 `stableKey` 查询用的是 0016 部署的索引。
