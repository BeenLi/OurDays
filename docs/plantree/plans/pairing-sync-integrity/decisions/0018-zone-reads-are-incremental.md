# Decision 0018 — 按 zone 增量拉取，本机留完整快照

- **日期**：2026-11-25　**状态**：Accepted　**PR**：#74
- **范围**：一次同步里所有批量读（对方的日程、评论、邀请、历史申请、昵称头像，自己 zone 里的评论和邀请，Mac 读自己的日程）

## 背景（原本的工作方式）
每路读取都是一次 `CKFetchRecordZoneChangesOperation`，但 change token 永远传 nil，返回的 token 丢掉，再在客户端按记录类型过滤。一次同步对对方的 zone 扫 5 遍、对自己的 zone 扫 3～4 遍，每遍都把整个 zone 下载一次，实测一次启动同步 13～20 秒，单路 4～10 秒。

下游有两处把"这次没拉到"当成"已删除"：`purgeStalePartnerMirrors`（对方的日程）和 Mac 的 `replaceOwnMirrors`（自己的日程）。重传判断（邀请回应、历史申请批复、评论删除）也拿"云端这份"和本地比。它们都默认手里是 zone 的完整内容。

## 决策
1. 新增 `ZoneChangeFeed`：每个 zone 一次拉取，带上次的 change token。它在本机留一份该 zone 的完整快照（归档的 `CKRecord` + token，放 Caches），把服务器这次报告的变更和删除合进快照，然后**仍然返回整个 zone**。记录只有服务器报告删除（`recordWithIDWasDeletedBlock`）时才离开快照，没被提到的原样保留。
2. 所以下游的删除和重传逻辑一行不改：它们拿到的还是完整列表，"不在列表里 = 已删除"继续成立。
3. 同一次同步里对同一个 zone 的多路读取共用一次请求；请求结束后才开始的读取会重新拉（写完再读一定读得到）。
4. 什么时候整个重拉：没有快照；token 被服务器拒绝（`changeTokenExpired`，包括 zone 删了重建）；快照满 7 天；这个版本要的字段或记录类型变了（签名不同）；快照文件读不回来。zone 不存在时连快照一起丢。
5. 快照按 iCloud 账号、环境（Development / Production）、数据库、zone 分文件；账号未知时不留快照，每次整拉。
6. 有记录服务器没能给出，或记录归档失败时，这次的结果照用，但不记 token，下次从旧 token 重新要一遍。
7. 拉取操作设为 `userInitiated`。

## 备选与理由
- **下游改成只处理增量**（只删服务器报告删除的那几条，导入只处理变化的）：要同时改 `purgeStalePartnerMirrors`、`replaceOwnMirrors`、三处重传判断和昵称头像的取值，每一处漏掉都是"把日历清空"或"把对方的昵称清掉"级别的问题，而且 SwiftData 里的本地状态是合并过本地操作的，不能当"云端这份"用。留一份原始记录的快照，把增量挡在读取这一层，改动只有一个文件。
- **回到 CKSyncEngine**：code-structure 0002 已经否决。
- **不设 7 天整拉**：目前没有已知会让快照和服务器不一致的路径，但一旦出现，用户没有任何办法自救；每周一次整拉的代价和现在的一次读取一样。

## 影响
- 不改 CloudKit schema，不改写入，旧版本不受影响。
- 第一次同步（或整拉）每个 zone 下载一次，之后只传变化。
- 快照丢了（系统清 Caches、重装）只是多一次整拉。
