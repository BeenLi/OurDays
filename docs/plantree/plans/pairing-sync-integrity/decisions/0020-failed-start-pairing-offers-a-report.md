# Decision 0020 — 「发起配对」失败时，可以复制一份诊断信息

- **日期**：2026-11-25　**状态**：Accepted

## 背景（原本的工作方式）
「发起配对」失败只在卡片下显示一行错误（0015 之后是真正失败的那条记录的错误码和 request id）。一对用户（两台 iOS 27.2.1，各自的 Apple ID）在 Production 都建不了分享（CKError 15），而他们的请求在 CloudKit Console 的日志里查不到，设备上的 OSLog 用户也发不出来。只靠截图里那一行，分不清是账号、这个 zone 里的旧状态，还是链接分享本身被拒。

## 决策
失败后在错误下面出现「复制诊断信息」。点了才收集，约 10 秒，结果放进剪贴板，由用户自己粘贴发给开发者：
- App 版本、系统版本、机型、语言地区、时区；
- iCloud 账号状态、userRecordID、私有库里的 zone、根记录现在的状态（有没有、挂没挂分享）；
- 这次失败的完整错误（userInfo、逐条错误、request id）；
- 分享探测：在一个临时 zone `OurDaysShareProbe` 里依次存一条普通记录、一个和「发起配对」一样的链接分享、一个仅受邀者分享，记下各自成败，然后删掉这个 zone。

怎么读探测结果：临时 zone 里链接分享能建，问题在 `CoupleSpace` zone 的现有状态；链接分享不行而仅受邀者可以，是这个账号不让建链接分享；两种都不行，是账号在这个容器里不能分享；连普通记录都存不了，是写入本身（比如空间已满）。

## 备选与理由
- 失败时自动收集并上传：没有服务器，也不该不经用户同意就发出 userRecordID。
- 把完整错误直接显示在界面上：太长，而且缺账号和 zone 的状态，也没有探测。
- 失败后自动换一种分享方式重试：还不知道原因，换方式会改变配对规则（见 CLAUDE.md 关于链接分享的约束）。

## 影响
- 正常配对路径没有变化；探测只在用户点按钮时运行，只碰临时 zone。
- 报告里有 userRecordID（配对双方本来就互相可见的那个 ID），不含日程内容、昵称或邮箱。
