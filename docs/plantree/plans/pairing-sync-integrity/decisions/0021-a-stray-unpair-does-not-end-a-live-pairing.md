# Decision 0021 — 误记的解除配对不会结束仍在进行的配对

- **日期**：2026-11-25　**状态**：Accepted（修订 0014 第 4 条）

## 背景（原本的工作方式）
0014 让配对日期在自己的设备之间接力，并记下「解除配对时间」`pairingClearedAt`（较晚的赢）。在这个时间之前开始的配对一律算已结束：不再上传，也不会被别的设备采用。

2.0 (39) 真机验证时，云端记录里有一条 11/25 16:01 的解除时间。它是当天某台测试设备（同一 Apple ID、Production 环境）在测试中走过解除或重置流程时留下的。可 iPhone 和伴侣一直配对着，并没有解除。结果 iPhone 的 10/15 被当成已结束的配对，云端记录里没有配对日期，新的 Mac 只能用共享根记录的创建日期（11/24）。任何设备只要误记一次解除，同一位伴侣仍然有效的配对日期就再也传不出去。

## 决策
1. 接力的配对日期多带一个 `confirmedAt`：自己的某台设备在解除时间之后，仍然确认跟同一个人配对着的时间。只要 `confirmedAt` 不早于解除时间，这段配对就仍然有效。
2. 一次同步解析完共享后，如果伴侣前后是同一个人、没有配对冲突、本机日期是亲眼看到的（不是反推的），而云端记着的解除时间会让这段配对失效，本机就记下确认时间，并在同一次同步里上传。每段配对每次解除最多确认一次，不会每次同步都写。
3. 同一位伴侣合并时，日期仍取最早，`confirmedAt` 取两边较晚的。
4. 真正解除配对时（`clearPairingState`），本机清掉日期和确认时间。之后没有设备再确认旧配对，旧日期照旧失效；和同一个人重新配对，会从新的一天算起。

## 备选与理由
- 解除时间带上伴侣 ID，只结束跟那个人的配对：和同一个人解除后再配对是正常情况，伴侣 ID 区分不了「误记」和「真的解除过」。
- 收到解除时间时，看自己的设备是否仍在配对，在仍在配对的设备上直接忽略：别的设备合并时还是会丢掉这段配对，Mac 照样拿不到日期。
- 删掉云端那条解除时间：每台设备本地都已经存了这个时间（较晚的赢），下一次同步又会写回去。

## 影响
- 没有新的 CloudKit 字段，`confirmedAt` 放在 `OwnSettings` 的 JSON 里。2.0 (39) 读到会忽略它。
- 一台设备没注意到另一台设备的解除，伴侣又很快重新配对时，这台设备会确认旧日期，配对天数会从旧日期算起。这种情况很少，而且接受这个代价。
