# Decision 0002 — 在开心的时刻请求 App Store 评分

- **日期**：2026-11-09　**状态**：Accepted　**PR**：#54

## 背景（原本的工作方式）
- App 从不调用系统评分接口，App Store 上 0 个评分。用户只有自己跑去商品页才能打分，几乎没人会这么做。

## 决策
1. 用 SwiftUI 的 `@Environment(\.requestReview)`（StoreKit 系统弹窗），由 `ReviewPromptPolicy.moment` 决定时机，只在两个「开心的时刻」请求：
   - **配对第 7 天**（`PairingDatePolicy.ordinalDayNumber >= 7`，已配对状态下）。
   - **第一次收到对方的评论**：本机出现对方写的、未删除、3 天内的评论。
2. 每个时刻每台设备只用一次（`SettingsStore.reviewPromptedMoments`），解除配对再配对也不重来；两次请求至少隔 3 天，同一次打开不会弹两次。
3. 时机检查在 `RootView`：启动、回到前台、根 sheet 关闭、评论数变化时；先等 2 秒让评论或日历先出现，有 sheet、配对冲突或换伴侣提示时不弹。
4. 带 `-ShareCal…` / `--sharecal-…` 启动参数（UI 测试、配对冒烟脚本）时不弹，避免弹窗挡住自动化。

## 备选与理由
- 设置里放「给我们评分」按钮：主动找按钮的人很少，系统弹窗在合适时机转化更高；以后可以再加。
- 按启动次数或使用天数弹：和「两人世界」的情绪无关，容易在用户刚遇到问题时弹出。
- 3 天之外的旧评论也算「第一次收到」：老用户升级后一打开就弹，那一刻并不开心，所以只看新到的评论。

## 影响
- 系统自己限流（每人每年最多 3 次，开发版每次都弹、TestFlight 不弹），所以「请求」不等于一定出现弹窗。
- 老用户升级后，若已配对满 7 天，会在下次打开时收到一次配对第 7 天的请求。
